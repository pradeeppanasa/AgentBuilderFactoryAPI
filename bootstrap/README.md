# Panasa Agent Factory — Bootstrap (Phase 11)

Two-stage Terraform per CLAUDE.md Section 9 / A13 / F13. Stage 0 creates the
remote state backend (and can't use it itself — chicken-and-egg). Stage 1
creates the Factory: Console + Runtime on ECS Fargate, all 11 DynamoDB
tables, EventBridge, Step Functions, CodeBuild, the 9 orchestration
Lambdas, and (optionally) a minimal self-hosted Langfuse.

Run this against **Panasa's own AWS account** for `DEPLOYMENT_MODE=prototype`,
or **the customer's account** for `DEPLOYMENT_MODE=enterprise` (R03/R04:
Panasa never holds the credentials that run this against a customer
account).

## Prerequisites

- Terraform >= 1.9, AWS provider ~> 5.0
- A git repo for generated Terraform (`GIT_REPO_URL`) — for github/gitlab/
  bitbucket you'll also need a PAT with repo write access; codecommit needs
  neither the repo pre-created nor a token (IAM auth).
- `bootstrap/scripts/build_lambda_package.sh` requires Python 3.12 + pip on
  whatever machine runs it (not necessarily the same machine running
  Terraform).

## Stage 0 — foundation

```bash
cd bootstrap/stage0
terraform init                       # local state — this stage creates the remote backend
terraform plan  -var="aws_region=eu-west-2" -var="environment=prototype"
terraform apply -var="aws_region=eu-west-2" -var="environment=prototype"
```

Mirror Panasa's images into this account's ECR (F13/A13 — the last
Panasa-controlled step):

```bash
PANASA_REGISTRY=public.ecr.aws/panasa VERSION=1.0.0 \
  ../scripts/mirror_images.sh "$(terraform output -raw account_id)" "$(terraform output -raw region)"
```

## Stage 1 — the Factory itself

1. Bridge Stage 0's outputs into Stage 1's backend config:

   ```bash
   ../scripts/generate_backend_config.sh > ../stage1/backend.hcl
   ```

2. Build the shared Lambda deployment package (needed before the *first*
   apply, and again any time `app/` or `lambda_handlers/` change):

   ```bash
   cd ../.. && ./bootstrap/scripts/build_lambda_package.sh && cd bootstrap/stage1
   ```

3. Init with the bridged backend config, then plan/apply, passing Stage 0's
   role/KMS/ECR outputs through and the git token (github/gitlab/bitbucket
   only — see `variables.tf`'s `git_token_value`, never written to a file):

   ```bash
   terraform init -backend-config=backend.hcl

   terraform plan \
     -var="kms_key_arn=$(terraform -chdir=../stage0 output -raw kms_key_arn)" \
     -var="agent_builder_runtime_role_arn=$(terraform -chdir=../stage0 output -raw agent_builder_runtime_role_arn)" \
     -var="deployment_role_arn=$(terraform -chdir=../stage0 output -raw deployment_role_arn)" \
     -var="git_repo_url=https://github.com/your-org/your-agent-iac-repo" \
     -var="ecr_repository_urls=$(terraform -chdir=../stage0 output -json ecr_repository_urls)" \
     -var="git_token_value=$GIT_TOKEN"

   terraform apply <same -var flags as above>
   ```

4. Populate the platform secrets Terraform deliberately left empty (Section
   11 Rule #3 — never in source):

   ```bash
   aws secretsmanager put-secret-value \
     --secret-id "$(terraform output -raw jwt_secret_arn)" \
     --secret-string "$(openssl rand -base64 48)"
   ```

   (`git_credentials_secret_arn`'s value is already set if you passed
   `git_token_value` above.)

5. Visit `terraform output factory_url`.

## Known gaps / deliberate simplifications

Surfaced here rather than silently shipped — fix these before relying on
this bootstrap for anything beyond a first bring-up:

- **RDS Postgres isn't in CLAUDE.md Section 9/A13's resource list at all.**
  Phase 3 (JWT auth) needs a real Postgres and nothing else provisions one,
  so `stage1/rds.tf` adds a single small instance. Split it before real
  production load, and before Langfuse (which shares it — see below) needs
  more than prototype-scale trace volume.
- **Self-hosted Langfuse (`stage1/langfuse.tf`) is Postgres-only** — no
  ClickHouse, no object storage. Fine for prototype-scale tracing; add
  Langfuse's documented full stack before real production trace volume.
  `LANGFUSE_PUBLIC_KEY`/`LANGFUSE_SECRET_KEY` also aren't produced by this
  bootstrap (they're generated by Langfuse's own org/project setup after
  first boot, not something Terraform can know ahead of time) — set them
  manually after Langfuse is up.
- **`SECURITY_SCANNING`'s 5 parallel CodeBuild branches share one
  DynamoDB stage key** (`codebuild/scripts/write_stage_result.sh`'s
  read-modify-write is documented safe only for *sequential* stages, which
  these five parallel branches are not — a pre-existing Phase 9 assumption,
  not introduced here). In practice a fast-finishing branch's result can be
  silently overwritten by a slower one's read-modify-write. Real fix:
  change `DeploymentRecord.stages` from a single JSON-string attribute to a
  native DynamoDB Map, so each branch can `SET stages.security_scanning_sast`
  atomically instead of rewriting the whole blob.
- **`policy_check.py` reconstructs a `SecurityFinding` from a plain-text
  `blocking_issue` string**, because none of the 6 buildspecs this
  bootstrap adds (`codebuild/sast-buildspec.yml` etc.) persist a
  structured, race-free findings list anywhere — only the per-stage
  status/summary `write_stage_result.sh` already wrote. It works because
  every buildspec here sets `blocking_issue` to one of
  `CRITICAL_BLOCK_CONDITIONS`'s exact category strings on failure, but it's
  a bridge, not the real design. Same gap, worse: RAGAS scores are never
  reconstructed at all, since `evaluation-buildspec.yml` has no real
  scoring harness yet (see below).
- **`evaluation-buildspec.yml` is a placeholder.** No phase up to and
  including Phase 10 ever built the thing that actually invokes an agent
  and scores it against RAGAS/PROMPT_EVALUATION/etc. — Phase 10 deliberately
  stopped at "starts this CodeBuild project" (same R05 boundary as
  security scanning). This stage always returns PASSED until that harness
  exists.
- **`deploying.py` / `health_check.py` are honest placeholders**, not real
  checks — no IaC template under `app/modules/iac_generator/templates`
  emits a per-agent ECS service name or health-check URL as an output, so
  there's nothing yet for these handlers to look up or probe. Add an
  `output` block to the api_gateway/orchestrator Terraform templates first.
- **`git_token_value` is a required `-var` input** (github/gitlab/
  bitbucket only) — CodeBuild's native source integration needs a
  registered credential before it can clone anything, and that credential
  can't be read back from a secret Terraform itself left unpopulated on a
  first apply. Supply it once via `-var`/`TF_VAR_git_token_value`
  (never committed) on the first apply; codecommit needs neither.
